# Corrections from the original release

This document exists because the code in this repository does not match the code that
was originally released alongside the manuscript, and that difference matters. This file
says exactly what changed, why, and how each issue was found, so that anyone comparing
this repository against an earlier version of the manuscript (or against the original
`Haneeshkm/CACC-V2X-dropout` release) can see precisely where the two diverge and why the
numbers moved.

If you only read one section, read [Bottom line](#bottom-line).

## Context

The manuscript's Methods section describes a specific algorithm (shared-policy multi-agent
TD3 with decentralised twin critics) and a specific reward function (six weighted terms,
Eq. 17). The code originally released alongside the manuscript did not implement either of
those things -- and separately, the released repository did not include the simulation
package (`cacc/`) at all, only the driving notebooks that import it. Rebuilding the
package from the manuscript's equations and the driving notebooks' usage, then verifying
it against the manuscript's own stated design, surfaced five distinct issues. All five are
fixed in this repository; every number in the current manuscript revision was generated by
the corrected code, not the original.

## The five issues

### 1. Centralised joint critic instead of decentralised twin critics

**What the manuscript claims:** "a decentralised per-agent twin critic
$Q_{1,2}(o_i,\xi_i)$ that scores only its own local observation and action... there is no
centralised critic or explicit joint-agent information during training" -- i.e. TD3, with
its two defining stabilisers (twin critics with a min-target, delayed policy updates,
clipped target-policy smoothing).

**What the original code did:** a single critic taking the concatenated observations and
actions of *every* agent (`n_agents * (obs_dim + act_dim)` input) -- textbook centralised
MADDPG (Lowe et al., 2017), the opposite of what the text describes. No twin Q, no target
smoothing noise, no delayed actor update.

**How it was found:** inspecting `maddpg.py`'s `CentralCritic` class definition directly
and comparing its input dimension against Table "RL training specification."

**Fix:** `cacc/maddpg.py`'s `TwinCritic` takes only `(obs_dim + act_dim)` inputs (10, matching
the paper's table) and is called once per agent, never on the joint state. `MADDPG.update`
implements clipped target-policy smoothing, a twin-critic min-target, and delayed actor
updates on a configurable `policy_delay` (default 2), matching TD3 (Fujimoto et al., 2018).
See `tests/test_maddpg.py::test_critic_is_decentralised_local_twin` and
`::test_delayed_actor_update_ratio`.

### 2. Reward missing two of its six terms

**What the manuscript claims (Eq. 17):** a headway-tracking term and a predecessor
speed-anchor term, in addition to safety, comfort, effort, and the string-amplification
term.

**What the original code did:** only four of the six terms; the tracking and speed-anchor
terms were absent from `PlatoonMARLEnv.step()`'s reward computation entirely.

**Fix:** added both terms to `cacc/marl_env.py`, using the weights given in Table
"RL training specification" ($w_{\mathrm{track}}=0.25$, $h_{\mathrm t}=0.8$s, scale
$c_{\mathrm t}=6.0$; $w_{\mathrm{vmatch}}=0.10$). Two clip constants
($\kappa_{\mathrm{track}}$, $\kappa_v$) are not given numerically anywhere in the
manuscript; the values used (`kappa_track=4.0`, `kappa_v=25.0` in `MARLConfig`) are
reasonable choices, not recovered values, and are flagged as such in the code. If you have
access to the original training configuration, please open an issue or PR with the correct
values.

### 3. Action map centred at the wrong point

**What the manuscript claims:** $u_i = \mathrm{clip}(6\xi_i, u_{\min}, u_{\max})$, so that
$\xi_i=0$ (the actor's near-zero-initialised starting output) commands zero acceleration
-- hold speed.

**What the original code did:** `a = a_min + 0.5*(u+1)*(a_max-a_min)`, a linear map from
$[-1,1]$ to $[a_{\min}, a_{\max}]$. At $\xi=0$ this commands $a = -1.5\,\mathrm{m/s^2}$ --
constant braking, not holding speed. This silently biased every rollout, training and
evaluation alike, toward braking from the very first gradient step.

**How it was found:** noticed while training a corrected TD3 implementation and observing
implausibly high collision rates early in training; traced to the action map by checking
what acceleration an all-zero action vector actually produced.

**Fix:** both `cacc/marl_env.py`'s environment step and `cacc/controllers.py`'s `RLPolicy`
now use `a = clip(6*u, a_min, a_max)`. Verified directly by tracing real acceleration
through 20 simulation steps with an all-zero action (`tests/test_maddpg.py::test_centred_action_map_holds_speed_at_zero_action`)
and through the standalone policy wrapper (`::test_rl_policy_centred_action_map`).

### 4. Evaluation harness never wired the gate's own inputs

**What this means:** the gate mechanism reads `dropout_flag` and `msg_age` from the
observation to decide how much to trust the communicated estimate. `Platoon.run()` (the
evaluation harness used to reproduce every table in the paper) never computed either field
-- they silently defaulted to 0.0 (`dropout_flag=0` meaning "link always up",
`msg_age=0` meaning "message always fresh"), regardless of what the V2X channel actually
did. Separately, `RLPolicy` fed the trained actor **raw physical units** (gap in metres,
speed in m/s) rather than the normalised values the network was trained on.

**Effect:** any trained gated policy evaluated through the original `Platoon` +
`RLPolicy` path saw garbage input at test time. Concretely, this is why an early version
of this project's own re-evaluation of a correctly-trained policy returned
$\Gamma^\star=0$ for every seed -- not because the policy was unusually good, but because
the evaluation harness handed it inputs so far outside its training distribution that it
produced a near-constant, do-nothing output that trivially "satisfies" zero amplification.

**Fix:** `cacc/marl_env.py` now exposes a shared `normalize_obs()` function used by both
the training environment and `RLPolicy`, so a trained actor sees the same input
distribution at test time as during training. `cacc/platoon.py`'s `Platoon.run()` now
tracks per-follower message age and computes `dropout_flag`/`msg_age` from the actual
channel state on every step, exactly mirroring `PlatoonMARLEnv`'s bookkeeping.

### 5. Training resume silently restarted the RNG stream

**What this means:** long training runs in this project were often split across multiple
process invocations (checkpoint, exit, resume) to fit compute constraints. The original
resume logic called `np.random.seed(seed)` / `torch.manual_seed(seed)` on *every*
invocation -- cold start and resume alike. Model/optimizer weights were correctly restored
from the checkpoint, but the *global* RNG stream (used by exploration noise, replay-buffer
sampling, and TD3's target-policy smoothing noise) was silently reset back to the seed's
starting point at every resume, rather than continuing from where training had left off.

**Effect:** two runs of "the same seed," chunked differently (e.g. three uneven
time-budget-based chunks vs. eight fixed 20-episode chunks), produced two different
stochastic realisations wearing the same seed label -- concretely, one specific seed's
final policy flipped from string-unstable to string-stable purely because of how the
training run happened to be chunked, with no code change and no different seed. Any
seed-specific claim made against a chunked training pipeline without this fix cannot be
trusted to be about "that seed" at all.

**How it was found:** retraining a "failed" seed with a different chunk schedule (for
periodic-checkpoint snapshotting) produced a different final outcome than the original
run. Diffing the two runs' code paths isolated the reseed-on-resume call.

**Fix:** `scripts/train.py`'s `save_checkpoint`/`load_checkpoint` now persist and restore
`np.random.get_state()`/`torch.get_rng_state()` alongside the model weights, with the
restore happening *after* the (harmless) cold-start reseed inside `build()`. A dedicated
regression test, `tests/test_reproducibility.py`, trains the same seed once continuously
and once split into five chunks and asserts the two produce numerically identical episode
returns; it fails immediately if this fix regresses.

**Retracted finding as a direct consequence:** an earlier, unpublished version of the
mixed-autonomy (penetration) sweep, run against the buggy pipeline, reported a training
seed that was fully string-stable at 100% penetration but catastrophically unstable
($\Gamma^\star=1.7$, 0% of evaluation seeds stable) at 75% penetration and below. After
fixing the RNG bug and retraining that seed from scratch, the finding did not reproduce:
the retrained seed is fully stable at every penetration level tested (see
`results/penetration_sweep/`). This is recorded here, rather than quietly dropped, as a
concrete illustration of why item 5 matters and why `tests/test_reproducibility.py`
should never be deleted.

## Bottom line

If you are trying to reconcile a number in this repository against an earlier draft of
the manuscript, a conference-submission version, or the original `Haneeshkm/CACC-V2X-dropout`
release, and it doesn't match: it's very likely one of the five issues above, not a
transcription error. Every number in the current manuscript was generated by the code in
this repository, with `results/` containing the raw output of the exact scripts that
produced it (see the main `README.md` for the table-to-script mapping).

## What was *not* found to be a bug

For completeness: the classical controllers (`PIDACC`, `MPCACC`, `CACC` -- but not the new
`SmoothCACC`, which is this revision's own addition, not part of the original release),
the vehicle dynamics, the IDM human-driver model, the V2X channel model, and the
string-stability transfer-function analysis were all checked and found consistent with the
manuscript's equations; none of the five issues above touch them. Tables and figures that
depend only on those components (the closed-form transfer-function results, the classical
dropout-handling ablation, the phase diagram, the bursty-vs-i.i.d. comparison for classical
controllers) are unaffected by this correction.

## Second round: corrections found during the Scientific Reports revision

The manuscript was substantially restructured and re-reviewed after the corrections above,
adding the mechanism-isolation analysis (`PlantInvertingCACC`), the dwell-hysteresis
ablation (`DwellHysteresisCACC`), and several new sweeps. That re-review process itself
surfaced further issues, listed here in the same spirit of full transparency.

### 6. Gilbert-Elliott channel parameters were not actually mean-matched

**What was claimed:** the "default" bursty-channel severity (`p_gb=0.05, p_bg=0.30,
drop_good=0.02, drop_bad=0.80`) had a stationary mean loss matched to the Bernoulli
comparison at `p=0.30`, so that "bursty vs i.i.d. at equal mean loss" was a clean,
single-variable comparison.

**What was actually true:** the analytic stationary mean loss for those parameters is
`pi_bad*eps_bad + (1-pi_bad)*eps_good = 0.131`, not `0.30` -- confirmed both analytically
and empirically (3e5 simulated channel steps). The comparison was silently confounded:
part of what looked like "burstiness matters" was actually "the bursty channel dropped
less than half as many packets on average."

**How it was found:** re-deriving the stationary distribution of the two-state Markov
chain by hand while responding to a reviewer question about GE parameterisation,
rather than trusting the values already in the script.

**The fix:** solved for two new configurations that are independently verified (both
analytically and empirically, with an assertion baked into
`scripts/run_ge_dropout_sweep.py` that runs on every invocation) to share the Bernoulli
channel's `p=0.30` mean loss while differing only in burstiness (mean bad-state dwell
0.33s vs 0.67s). Re-running the learned controller's evaluation under the corrected
channel changed the finding: at genuinely matched mean loss, the milder burst is
essentially harmless, but the more severe burst causes real failures in seeds that
handle i.i.d. loss fine (including one sharp failure, Gamma*=1.45). The corrected
finding is more concerning, not less -- this was not a case where fixing the bug made
the paper's story go away.

### 7. Frequency-sweep horizon was inconsistent with every other table at the shared benchmark point

**What was claimed:** the per-seed frequency-sensitivity sweep (Section 2.6) reported
Gamma* at omega=0.45 as directly comparable to the main gate-ablation and benchmark
tables, which also evaluate at omega=0.45.

**What was actually true:** `run_frequency_sweep.py` computed its simulation horizon as
`T = max(60.0, 4.5 * (2*pi/omega))`, which gives `T ~= 62.8s` at omega=0.45 -- not the
fixed `T=120s` (`CANONICAL_T`) used by every other evaluation in this project. The
sweep's own omega=0.45 point therefore did not reproduce the same seed's value in the
gate-ablation table for what should have been an identical computation.

**How it was found:** cross-checking a number quoted in the frequency-sweep section
against the corresponding entry in the gate-ablation table during a line-by-line
consistency pass, and finding they disagreed for what was supposedly the same
condition and seed.

**The fix:** changed the horizon formula to `T = max(CANONICAL_T, 4.5*(2*pi/omega))`, so
it only extends beyond 120s at genuinely low frequencies that need a longer window for
enough disturbance cycles, and matches the canonical protocol everywhere else. Re-ran
the full per-seed sweep for all four successful seeds and both extended-frequency-
training seeds; `tests/test_controllers_and_metrics.py::test_frequency_sweep_uses_canonical_horizon_at_shared_benchmark_point`
locks this in as a regression test. The qualitative conclusion (each seed fails in a
different, non-overlapping frequency sub-band) was unchanged by the fix; only the
specific decimal values shifted.

### 8. Assorted numeric and writing errors found during a full verification pass

A dedicated line-by-line check of every number in the manuscript against the actual
simulation outputs (rather than trusting arithmetic done earlier in the drafting
process) found and fixed:

- The mixed-autonomy penetration-robustness range was stated as `Gamma*` in
  `[0.65, 0.85]`; the actual range across the four successful seeds and four tested
  penetration levels is `[0.588, 0.925]` -- both bounds were wrong.
- The Gilbert-Elliott severe-burst results were mischaracterised in prose: `f_stable=0.80`
  was described as "mostly unstable" (it means 4 of 5 evaluation seeds *stable*), and
  "two of four seeds fully stable" was stated when only one seed actually had
  `f_stable=1.00`.
- Table 2's standard deviations for the learned controller's minimum-gap and TTC columns
  were computed incorrectly by hand (stated 3.3 and 5.9; the correct values, recomputed
  directly from the raw per-seed data, are 2.9 and 5.3).
- A window-length (`M=2,3,5` disturbance cycles) sensitivity check quoted in Table 1's
  caption did not match Table 1's own headline `M=3` value, which is a logical
  impossibility since `M=3` *is* the canonical protocol. Recomputed with
  `scripts/run_mechanism_ablation.py`.
- A missing `\subsection{}` heading (accidentally deleted during an earlier edit, leaving
  a `\label` with no heading above it), a stray double-backslash that silently broke
  LaTeX math mode, straight quotation marks where curly LaTeX quotes were intended, and
  14 bibliography entries that were defined but never actually cited in the text
  (including the authors' own prior related work) were all found and fixed during the
  same pass.
- Figure "per-vehicle steady-state velocity amplification" originally quoted a peak
  `Gamma*~=1.27` that could not be reproduced from any documented parameter set or seed;
  it was regenerated from scratch as a 5-seed mean+/-std (`scripts/make_fig_amplification.py`),
  which gives peak `Gamma*~=1.12` -- the figure and caption now state only numbers that
  come directly from a script in this repository.
- Figure "learned controller versus classical baselines" only had two dropout-probability
  data points (`p=0.3, 0.6`) loosely connected by a line; regenerated
  (`scripts/make_fig_rl_benchmark.py`) with a real continuous sweep over
  `p in [0, 0.1, ..., 0.6]` for all four successful seeds plus the naive baseline.

None of these eight issues change the paper's central claims (headway switching, not
information loss, is the destabilising mechanism; the learned controller closes most but
not all of the resulting robustness gap). Several make the paper's supporting evidence
more accurate and, in the Gilbert-Elliott case, reveal a real limitation that the
original, buggy comparison had been masking.
